## Phase Goal

**As an** invited company admin, **I want to** set up my workspace, team, and product portals, **so that** my customers have a branded place to visit.

**This plan's slice (the phase tracer):** the outcome end of the story first. A signed-out visitor opens `/{ws}/{product}` and gets that product's portal shell, served by the web app from an allowlisted public API response over the new tenancy tables. This proves the riskiest architecture first: a root dynamic `[ws]` route beside static app routes under vinext, a route-group shell split, a Drizzle migration at boot, and a public DTO that fails closed. Creating workspaces and products through the UI arrives in later plans; here the rows are seeded by tests.

<objective>
Wire GET /{ws}/{product} through every layer: workspaces/products tables (migration 0002) → PortalGuard + PortalController (public, explicit select, Zod-strip serializer) → RSC layout via apiServer → portal frame. Then split the root layout so portals get their own frame while app pages keep the Phase 1 header, and handle every non-happy state on the path (unknown, deleted, suspended).

Purpose: the public portal is the product's promise to customers (PROD-04), and the `/{ws}` root segment is the routing decision every later phase builds on.
Output: tenancy schema + migration, portal module, shell split, portal frame, state components, API and stack tests.
</objective>
