## Phase Goal

**As an** invited company admin, **I want to** set up my workspace, team, and product portals, **so that** my customers have a branded place to visit.

**This plan's slice:** the invited admin's first minutes. They open the link, sign in with the matching email, create their workspace with a name, a URL, and a logo, and become its owner. Wrong account, expired, used, revoked, and broken links each explain themselves. The owner sees the invite turn into "Used by {name} · {workspace}".

<objective>
Add the invite lookup API and the /invite/{token} page (platform kind; 02-07 adds the workspace kind). Let a verified platform-invite holder create a workspace, claiming the invite atomically in the same transaction. Add the optional logo to workspace creation through a reusable LogoField, which needs the upload id that Phase 1's upload response does not return yet.

Purpose: completes WORK-01 (invite-only creation with name, slug, and uploaded logo) and closes the PLAT-02 loop.
Output: invites controller + service methods, invite page, proxy matcher, LogoField, upload id, API and stack tests.
</objective>

## Flagged assumptions (carried, not silently dropped)

- **RESEARCH A4:** a platform invite is consumed at workspace creation and matched by email, not by token. A verified user with a pending invite for their email can create a workspace without opening the link. That has the same security as D-14's email binding.
- An unverified OAuth email that equals the invite email is treated as a mismatch (D-16 says verified). The page copy then says "signed in with a different account"; the user must verify the email with their provider.
- Deferred, not planned (CONTEXT Deferred Ideas): owner or inviter approval of a mismatched claim.
