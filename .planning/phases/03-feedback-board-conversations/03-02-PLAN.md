## Phase Goal

**As a** customer, **I want to** post, vote on, and discuss ideas on a product's board, **so that** the team sees what I actually need.

**This plan's slice (the phase tracer):** the core loop first. A signed-in customer opens a product's board, submits a post, lands on its permanent link, and sees it on the board. This proves the riskiest architecture end to end: per-product numbering under a row lock, an author DTO that can never carry an email, the vinext permalink page with a page-level redirect, and the full Phase 3 data model applied by a migration at boot. Votes, filters, comments, moderation, and email expand from this slice in later plans.

<assumption_delta_decision>
The detector fired on "merge into another", "also reassign", and "optional public note". None changes an identity model; the one real seam is that posts gain a second identifier.
- Primary noun: **post**, publicly identified by (product, number); the uuid stays the internal primary key and never leaves the API.
- Decision: **add-alongside** — the per-product number is added beside the uuid because permalinks (D-12) are a published contract and must be short and stable; the uuid remains the FK target for votes/comments.
- Accepted debt: none forcing a promote. A later "move post between products" feature would force renumbering and is out of v1 scope.
</assumption_delta_decision>

<objective>
Wire "submit a post and read it back" through every layer: the Phase 3 schema (migration 0007) → PostsService/PortalPostsController (public reads with explicit selects into Zod-stripped Public* DTOs, signed-in create) → RSC board and permalink pages. Then confirm the redirect contract with the human (Task 2, D-12 one-way) and finish the permalink and sign-in round trip.

Purpose: every later Phase 3 plan writes into these tables and renders through these pages.
Output: schema + migration, shared contracts, feedback module, board/permalink pages, PlainText, tests.
</objective>
