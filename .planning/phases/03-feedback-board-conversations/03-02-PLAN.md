## Phase Goal

**As a** customer, **I want to** post, vote on, and discuss ideas on a product's board, **so that** the team sees what I actually need.

**This plan's slice:** the data and contract half of the phase tracer. A signed-in client can create a post and read it back through the public portal API, with per-product numbering under a row lock, an author DTO that can never carry an email, the whole Phase 3 data model applied by a migration at boot, and tenant isolation proven for portal routes. Plan 03-04 puts the web pages on top of exactly these endpoints.

<assumption_delta_decision>
The detector fired on "merge into another", "also reassign", and "optional public note". None changes an identity model; the one real seam is that posts gain a second identifier.
- Primary noun: **post**, publicly identified by (product, number); the uuid stays the internal primary key and never leaves the API.
- Decision: **add-alongside** — the per-product number is added beside the uuid because permalinks (D-12) are a published contract and must be short and stable; the uuid remains the FK target for votes and comments.
- Accepted debt: none forcing a promote. A later "move post between products" feature would force renumbering and is out of v1 scope.
</assumption_delta_decision>

<objective>
Ship the Phase 3 schema (migration 0007), the shared contracts and error codes, and the public post endpoints end to end at the API level, then harden the contract: numbering under concurrency, validation, merged-post redirects, 404s, the no-email canary, and portal isolation.

Purpose: every later Phase 3 plan writes into these tables and reads through these DTOs; publishing them first keeps later plans migration-free (except 03-05's backfill).
Output: schema + migration, packages/types feedback contracts, feedback module, API tests.
</objective>
