# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** this phase extends `01-UI-SPEC.md` and `02-UI-SPEC.md` (both approved). It does not replace them. Every Phase 1 and Phase 2 token, component, layout rule, accessibility rule, and copy rule still applies unless this file overrides it. Phase 3 adds these surfaces:

1. **Portal board** at `/{ws}/{product}`. It replaces the coming-soon body and adds the `Feedback` tab.
2. **Portal post page** at `/{ws}/{product}/p/{number}-{slug}`, with the comment timeline and inline admin menus.
3. **Dashboard board** at `/dashboard/{ws}/{product}/board`, the dashboard post detail page, and the category editor.
4. **Account settings** at `/account` (comment-email toggle and account deletion), and the **unsubscribe / mute landing page** at `/unsubscribe/{token}`.
5. **Comment digest email**, as plain text plus simple HTML.

**Override of Phase 2:** Phase 2 said "the portal never renders admin UI or admin links". Phase 3 D-01 amends that. The portal now renders an inline admin menu on posts and comments, **only** when `/me` shows the viewer is a member of the workspace. The server still authorizes every admin action, and it alone decides the `Admin` badge.

**Mode:** generated without interactive questions. 03-CONTEXT.md locks D-01 to D-25, and the open areas are all listed under Claude's Discretion. Values not locked upstream are marked *(Claude's choice)*. The user can override any of them before planning.

## Spacing Scale

These are the Phase 1 and Phase 2 values, unchanged. All are multiples of 4, on Tailwind's 4px step.

| Token | Value | Tailwind | Usage (Phase 3 additions) |
|-------|-------|----------|---------------------------|
| xs | 4px | `1` | Title-to-excerpt gap in a post row, `ChevronUp`-to-count gap in the vote box, wrapped meta-row line gap |
| sm | 8px | `2` | Toolbar gaps, meta row gaps, author line gaps, comment actions row, composer stack, selection bar gaps |
| md | 16px | `4` | Post row padding and vote-box-to-text gap, avatar-to-text gap in comments and activity, reply list top margin, note box padding |
| lg | 24px | `6` | Board page stack, timeline item gap, comment section stack, tab-to-filters gap |
| xl | 32px | `8` | Post page section stack, comments section top padding |
| 2xl | 48px | `12` | Reply indent (`pl-12`) and comment body indent: a 32px avatar plus a 16px gap, so reply text lines up with the parent's text. Also the portal and dashboard main vertical padding from 640px up. |
| 3xl | 64px | `16` | Not used |

Exceptions (fixed component dimensions, all multiples of 4, not spacing tokens):
- `VoteButton`: 48×56px (`w-12 h-14`).
- The activity icon well and the deleted-stub circle are 32px (`size-8`), matching the avatar.
- Category rows are 56px tall. Voter rows and the selection bar are 48px tall.
- Toolbar selects are 160px wide (`w-40`) on the portal and 176px (`sm:w-44`) on the dashboard. The dashboard search is 288px (`sm:w-72`). The board table's title cell caps at 320px (`max-w-80`).
- The search input's left padding is 36px (`pl-9`): a 12px inset plus the 16px icon plus an 8px gap.
- Touch targets: row-action triggers and the comment actions trigger are 32px (`size-8`). `Reply`, `MuteToggle`, and the back link are `sm` buttons (32px tall). The vote box is 48×56px.
- `-ml-3` on the back links (see Layout). Phase 2's `-mb-px` TabNav rule still applies.

No arbitrary values beyond Phase 2's (`w-[calc(100%-32px)]`, `text-[var(--primary-text)]`, `bg-[var(--entity-accent)]`).

## Interaction Contracts

### Board (`/{ws}/{product}`; POST-01, POST-03, POST-04, POST-07 to POST-11, D-07 to D-11)

- **Rendering:** an RSC fetches the first page (20 posts *(Claude's choice)*) with the current URL params, and renders the header, toolbar, list, and `Load more`. A client component takes over the list for later pages and votes.
- **URL params (nuqs, `shallow: false` so the RSC re-fetches on change):**

  | Param | Values | Default (omitted from URL) |
  |-------|--------|----------------------------|
  | `q` | search text, trimmed, 1–100 characters | none |
  | `sort` | `top`, `new`, `match` | `top`; `match` when `q` is set |
  | `category` | category id | all categories |
  | `status` | `all`, or a status id | open (hides Completed- and Closed-type statuses, POST-09) |
  | `new` | `1` | absent. Removed from the URL when the dialog closes. |

  Changing any of them replaces the list from the first page (a new history entry, so Back restores the previous view, D-11). Search commits on Enter and when the native clear button empties the field. It does not run on every keystroke, matching Phase 2's platform search. Selects commit on change.
- **Sort select options:** `Top voted`, `Newest`, plus `Best match`, which appears first and is the default only while `q` is set. Clearing the search drops `match` and returns to `Top voted` *(Claude's choice for D-discretion "FTS ranking vs Top Voted": search defaults to relevance, and the user can still pick another sort)*. Top voted breaks ties by newest.
- **Category select:** `All categories`, then each category in creation order. Hidden entirely when the product has no categories.
- **Status select:** `Open`, `All statuses`, then each status in the product's order.
- **Labels:** each control has a visually hidden `<label>`: `Search posts`, `Sort by`, `Category`, `Status`.
- **Load more:** fetches the next page with the server's opaque cursor, using the same filters. While pending, the button shows `LoaderCircle` + `Loading…` and is disabled. New rows append, and focus stays on the button. A visually hidden `aria-live="polite"` region announces `Loaded {n} more posts`. When no further page exists, the button is removed. The cursor is never written to the URL, so a refresh shows the first page again.
- **Voting (POST-03, POST-04):**
  - Signed in: clicking toggles the vote **optimistically**: fill and count change at once, then a `PUT` (vote) or `DELETE` (unvote) is sent. On failure the button reverts and an error toast shows `Couldn't save your vote. Try again.` (`toast.error`; votes have no inline home, so this is the second toast-for-failure exception after Phase 2's reorder). Double clicks are harmless, because the API is idempotent. A click while a request is in flight queues the final state.
  - Signed out: clicking navigates to `/login?next={current path + query}`. It does not auto-vote after sign-in (PROD-06: return to the same place).
  - An author's own new post starts with their vote, filled, at a count of 1, and they can remove it (D-10).
- **New post (D-08, PROD-06):**
  - Signed in: `New post` opens `PostFormDialog` in create mode.
  - Signed out: `New post` is a link to `/login?next={/ws/product?…&new=1}`. On return, the board opens the dialog because `new=1` is present.
  - Fields, in order: `Title` (`Input`, required, 3–120 characters), `Details` (`Textarea`, optional, up to 5,000 characters), `Category` (`NativeSelect`, required when the product has at least 1 category; the first option is a disabled placeholder `Choose a category`; hidden when there are no categories).
  - Validation runs on blur and on submit (Phase 2 rule).
  - Submit: `Submit post` (pending `Submitting…`, fields disabled). On success: navigate to the new permalink, then toast `Post submitted`. Server errors render as an `Alert` above the footer, and the dialog stays open with the input kept.
  - Closing the dialog with unsaved text discards it without asking. The footer's dismiss button is named `Discard post` so that is clear.
- **Empty and no-match states:** see Copywriting. A filtered empty state offers `Clear filters`, which links to the bare board path.

### Post page (`/{ws}/{product}/p/{number}-{slug}`; POST-05, POST-06, POST-11, AUTH-04, CMNT-01 to CMNT-04, D-12 to D-20)

- An RSC fetches the post, the timeline, and the viewer's relationship (`voted`, `isAuthor`, `inConversation`, `muted`, `canEdit`, `canDelete`). The server decides `canEdit` / `canDelete` from D-13 / D-14. The UI never computes the lock itself.
- **Edit post:** `Edit post` opens `PostFormDialog` in edit mode, prefilled. Footer: `Discard changes` (`outline`) and `Save post` (`default`, pending `Saving…`, disabled until the form is dirty). On success the dialog closes, the page refreshes in place, the `edited` marker appears, and the toast reads `Post updated`. Saving a new title changes the slug, and the URL is replaced with the new canonical one (`router.replace`, no extra history entry).
- **Delete post:** the author's delete and the admin's delete use the same `ConfirmDialog`, with different body copy (see Destructive confirmations). On success: navigate to the board and toast `Post deleted`.
- **Locked post (author):** both menu items are disabled with the reason line. If someone engages while the dialog is open, the server returns `post_locked` and the dialog shows that `Alert` (see error mapping).
- **Comment composer (CMNT-01):**
  - Signed in: the `Textarea` (label `Write a comment`, placeholder `Add a comment…`, required, up to 5,000 characters). Submit is `Post comment` (`default`), pending `Posting…`, with the textarea disabled.
  - It is **not** optimistic. On success the new comment is appended to the timeline from the server response, the textarea clears, focus moves to the new comment's `<li>` (`tabIndex={-1}`), and there is no toast. The viewer is now in the conversation, so `MuteToggle` appears.
  - On failure an `Alert` renders under the textarea and the text is kept.
  - Signed out: `SignInPrompt` with `Sign in to comment`, linking to `/login?next={post path}#comment`. `safeNext` keeps the hash, so the browser lands at the composer.
- **Reply (D-16):** `Reply` on a top-level comment or on any reply opens the reply composer at the end of that top-level comment's replies, with the textarea focused. A reply to a reply attaches to the same top-level parent. Submit `Post reply` (`default` `sm`, pending `Posting…`), dismiss `Discard reply` (`ghost` `sm`). Signed out, `Reply` links to the sign-in URL with `#comment-{parentId}`.
- **Edit comment (CMNT-03, MOD-01):** `Edit comment` swaps the body for a prefilled `Textarea`, with `Discard changes` (`ghost` `sm`) and `Save comment` (`default` `sm`, pending `Saving…`, disabled until changed). Esc triggers `Discard changes`. On success the body updates in place, the `edited` marker appears, and focus returns to the `Comment actions` trigger. No toast.
- **Delete comment (CMNT-04, MOD-02):** a `ConfirmDialog`. On success the comment is removed, or replaced by the `[Comment deleted]` stub when it has visible replies (D-18), and the toast reads `Comment deleted`. Focus moves to the `Comments` h2.
- **Mute toggle (D-25):** clicking applies immediately (not optimistic, the button is disabled while pending). Success toasts: `You won't get emails about this post` / `You'll get emails about new comments on this post`.
- **Change status (MOD-03; admins, portal and dashboard):** `StatusChangeDialog`, titled `Change status`.
  - Fields: `Status` (`NativeSelect`, every status, preselected to the current one) and `Public note` (`Textarea`, optional, up to 1,000 characters, helper `Shown on the post with your name.`).
  - Footer: `Discard changes` (`outline`) and `Change status` (`default`, pending `Saving…`, disabled until a different status is chosen).
  - On success the dialog closes, the post's status badge updates, an `ActivityItem` is appended to the timeline, and the toast reads `Status changed to {status}`.
  - A status change does **not** send email. Only comments trigger the comment email.
- **View voters (MOD-04):** opens `VotersDialog`. The public only ever sees the count.
- **Merge into… (MOD-05, D-03, D-04):** `MergeDialog`, titled `Merge into another post`.
  - **Step 1, pick:** a search `Input` (`type="search"`, autofocused, label `Find the post to keep`, placeholder `Search posts in {product}`) and a results list below it. With an empty query the list shows the 8 most-voted posts. Typing runs the board FTS search after a 300ms pause (local state, not the URL). Results exclude the current post and deleted posts. Each result is a full-width `<button>` (`flex items-center gap-4 p-4 rounded-md hover:bg-muted text-left`) showing the vote count (14px / 600, `w-12 text-center tabular-nums`), the title (14px, `line-clamp-2`), and the `StatusBadge`. Footer: `Close` (`outline`). No-match text: `No posts match "{q}".`
  - **Step 2, confirm:** the same dialog shows `"{duplicate}" ({a} votes)` → `"{target}" ({b} votes)` as two `rounded-lg border p-4` boxes with a lucide `ArrowDown` between them, then the body copy. Footer: `Choose another post` (`outline`, back to step 1, keeping the query) and `Merge posts` (`destructive`, pending `Merging…`).
  - On success: navigate to the target's page (portal permalink, or the dashboard detail page when started there), and toast `Posts merged`. The merged post's old URL now returns a 301 to the target, and the target shows no "merged from" trace (D-04).
- **Page metadata:**
  - `<title>`: `{post title} · {product}`.
  - `meta description` and `og:description`: the first 160 characters of the description, cut at a word boundary, or the board fallback description when empty.
  - `og:title`: the post title.
  - `<link rel="canonical">`: the absolute canonical permalink.
- **Board metadata:** `<title>` is `Feedback · {product}`. Everything else stays as in Phase 2.

### Dashboard board (`/dashboard/{ws}/{product}/board`; MOD-01 to MOD-05, D-01 to D-06)

- **Posts tab:** filters use the same `nuqs` params as the portal, with dashboard defaults: `status=all`, `sort=new`. The sort options are `Newest`, `Top voted`, and `Best match` while searching *(Claude's choice: admins triage the newest first)*. Pages of 50, with `Load more`.
- **Selection:** row checkboxes select posts. The header checkbox selects every loaded row, and shows `indeterminate` when only some are selected. The selection clears when filters change.
- **Bulk merge (D-03):** `Merge posts…` opens `BulkMergeDialog`, titled `Merge {n} posts`.
  - A native radio group (`role="radiogroup"`, label `Keep this post`) lists the selected posts. Each option row is `flex items-center gap-4 p-4` with the radio, the title (14px / 600), and `{votes} votes · {comments} comments` (14px muted). The post with the most votes is preselected.
  - Then the body copy. Footer: `Keep all posts` (`outline`) and `Merge posts` (`destructive`, pending `Merging…`).
  - On success the dialog closes, the table reloads, the selection clears, and the toast reads `{n} posts merged into "{title}"`.
- **Row actions:** `PostActionsMenu` (admin). `Edit post` opens `PostFormDialog` in edit mode. `View voters` opens `VotersDialog`. `Merge into…` opens `MergeDialog`. `View on portal` opens the permalink in a new tab. `Delete post` opens the admin delete confirm.
- **Deleted tab (D-06):** two sections, each with an h2 (16px / 600) and a table:
  - `Deleted posts`: columns Post (title, not a link), Deleted (`formatDate`), Deleted by (name, or `Author` when the author deleted it), and the action `Restore` (`ghost` `sm`, `aria-label="Restore {title}"`).
  - `Deleted comments`: columns Comment (the first 80 characters, `truncate`), On post (title, linking to the dashboard detail page), Author, Deleted, and the action `Restore`. When the comment's post is itself deleted, `Restore` is disabled and the cell shows the 12px muted line `Restore the post first`.
  - Restore is reversible, so it has **no confirmation**. On success the row leaves the list and the toast reads `Post restored` or `Comment restored`. The item returns unchanged, and a restored post's votes count again.
  - Each section has its own empty line (14px muted) when empty. The `Deleted` tab with both empty shows the EmptyState instead.
- **Dashboard post detail:** described in Layout. `Change status` opens `StatusChangeDialog`. The comment composer posts as the admin, and the comment appears publicly with the server-decided `Admin` badge (D-02). Admins see the same timeline as the portal: deleted comments are absent here too, and they are restored from the `Deleted` tab.

### Category editor (`/dashboard/{ws}/{product}/categories`; POST-02)

- PageHeader `Categories`, with a description and the action `Add category` (`default`).
- **Add and rename** use a `Dialog` (`Add category` / `Rename category`) with one field, `Name` (1–30 characters, unique per product, case-insensitive). Footer: `Discard changes` (`outline`) and `Add category` / `Save category` (`default`, pending `Saving…`). On success the dialog closes and the toast reads `Category added` or `Category renamed`.
- **Row menu:** `Rename category`, separator, `Delete category` (destructive). Delete opens a `ConfirmDialog`. Its posts keep existing with **no category** *(Claude's choice: simpler than a reassignment picker, and categories are optional metadata)*. Toast: `{name} deleted`.
- A product may have zero categories. The New post form then hides the Category field, and the board hides the Category filter.
- New products are seeded with `Feature Request`, then `Bug`, in that creation order, in the same transaction that seeds statuses.
- Empty state: see Copywriting.

### Account settings (`/account`; NOTF-02, WORK-07, D-20, D-25)

- PageHeader `Account`, description `Signed in as {name}.`
- **Comment emails section:** a native checkbox (`size-4 accent-foreground`) labelled `Email me about new comments on posts I'm part of`, with helper copy. Toggling applies immediately: the checkbox is disabled while the request runs, then the toast reads `Comment emails turned on` or `Comment emails turned off`. On failure the checkbox reverts and an `Alert` renders under it. There is no Save button.
- **Danger zone:** body copy, then `Delete account` (`outline` with `text-destructive border-destructive/30`), opening a `ConfirmDialog` with a type-to-confirm `Input` labelled `Type DELETE to confirm`. Confirm stays disabled until the trimmed value equals `DELETE` exactly.
  - On success: the session ends, `flash("Your account was deleted")` is stored, and the page calls `window.location.assign("/")`.
  - **Owned workspaces (user decision, CONTEXT D-26):** a user who owns one or more workspaces can still delete their account. Before the type-to-confirm step, the dialog shows a `Your workspaces` step listing each owned workspace (logo, name, `{n} products · {n} posts`). Each row asks the owner to pick one of two choices with a native radio group (`role="radiogroup"`, label `What happens to {workspace}`):
    - `Transfer ownership to…` followed by a `NativeSelect` of that workspace's other members (admins). This option is disabled with the 12px muted reason `No other members to transfer to` when the owner is the only member.
    - `Delete this workspace`, with the 14px destructive line `Its products, portals, posts, and comments are removed for everyone.`
    `Continue` (`default`) stays disabled until every workspace has a choice, and every transfer has a member selected. The type-to-confirm step then repeats a plain summary (`{workspace}: transferred to {name}` / `{workspace}: deleted`) above the body copy. The server applies all choices and the account deletion in one transaction and rejects a request that leaves any owned workspace unresolved with `owned_workspaces_unresolved`. Deleted workspaces are soft-deleted (the Phase 2 D-18 product rule extended to workspaces): their portals and `/{ws}` page return the normal not-found page.
  - **Platform owner:** the account whose email matches `PLATFORM_OWNER_EMAIL` can't be deleted from the UI (the identity lives in server config). The button is disabled, and the danger-zone body shows the platform-owner copy. The server returns `platform_owner_account`.
  - After deletion, the user's posts and comments show `Deleted user` with the fallback avatar. Their votes still count. Their workspace memberships are removed. They receive no further email (D-20).

### Unsubscribe and mute landing page (`/unsubscribe/{token}`; NOTF-02, D-25)

- The token is signed, does not expire, and encodes the user and a scope: **all comment emails** or **one post**.
- The page **never changes anything on GET**, because email security scanners prefetch links. It shows a confirm button that sends a `POST`. The RFC 8058 `List-Unsubscribe-Post` one-click header is handled by the API directly and turns off all comment emails.
- No sign-in required. States and copy are in the Unsubscribe pages table. After success, the page shows an undo button in the done state (`outline`), which posts the reverse change.

### Comment email (NOTF-01, NOTF-03, OPS-03, D-21 to D-24)

- **One email per recipient per workspace per batch window.** Sections are grouped by post, ordered by the most recent new comment first. Within a section, the latest up to 3 new comments appear oldest to newest, then `+{n} more comments` when there are more.
- **Snippet rule:** collapse all whitespace to single spaces, then cut to at most 200 characters at the last word boundary and append `…`. Text of 200 characters or less is shown whole. Comments deleted before the send are left out. A section with no remaining comments is dropped, and an email with no sections is not sent. The snippet helper ships with one unit test (short text, long text, a single 250-character word, collapsed newlines).
- **Every user-supplied string is HTML-escaped** in the HTML part: names, titles, snippets, and the workspace and product names.
- **Headers:** `From: "{workspace} via UserHQ" <{SMTP sender}>`. `List-Unsubscribe: <{origin}/api/v1/unsubscribe/{allToken}>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`.
- **HTML layout** (inline styles only; no images, no web fonts, no external CSS):
  - Outer: white background. A single centered table, `max-width:560px`, `padding:24px`, `font-family:-apple-system,BlinkMacSystemFont,"Segoe UI",Roboto,Helvetica,Arial,sans-serif`, text `#0A0A0A`.
  - The intro line, 14px `#525252`.
  - Each post section: `border-top:1px solid #E5E5E5; padding:24px 0`. The product name (12px / 600 `#525252`), then the post title (16px / 600, linked to the permalink, `#0A0A0A`), then each comment as the commenter's name (14px / 600, with ` · Admin` appended for admin commenters) and the snippet (14px / 400, `line-height:20px`, `margin:4px 0 16px`), then `+{n} more comments` (14px `#525252`), then a links row (14px): `View post` · `Mute this post`, both `#171717` underlined.
  - Footer: `border-top:1px solid #E5E5E5; padding-top:24px`, 12px `#525252`: the reason line and the `Turn off comment emails` link.
- **Plain-text part:** the same content and order. Sections are separated by a blank line and a `---` line. Links are written out in full after their labels.

### Accessibility (in addition to Phases 1 and 2)

- `VoteButton` is a real `<button>` with `aria-pressed`, and its label includes the post title and count, so a list of vote buttons is distinguishable to screen readers.
- The post list is a `<ul>` and the timeline is an `<ol>`, with nested `<ol>`s for replies. Each comment `<li>` has an `id` so links like `#comment-{id}` scroll to it.
- Every `<time>` carries `dateTime` and a `title` with the full date and time.
- Autolinks opening in a new tab use `target="_blank"` with the required `rel`. Their visible text is the URL itself.
- After a successful delete of a post, comment, or category, focus moves to the nearest stable heading (`h1` or the `Comments` h2), because the trigger is gone.
- Live region announcements: `Loaded {n} more posts` after Load more, and the result count after a merge search (`{n} posts found`).
- Disabled menu items with a reason (post lock, restore blocked, platform-owner account deletion, transfer with no other members) show the reason as visible text, never as a tooltip only (Phase 2 rule).
- Color is never the only signal: a voted box is also announced through `aria-pressed`, statuses always show their name, and the `Admin` badge has text.
