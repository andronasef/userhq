## Phase Goal

**As an** admin, **I want to** plan privately and share a public roadmap, **so that** users hear back when their feedback moves.

**This plan's slice:** The closing-the-loop notification and activity engine. We implement stakeholder status change discovery (author, voters, commenters), atomic grouped notification upserts, notification center endpoints, and the "My Activity" product feed with session visit diffing (`hasStatusChange`, `hasNewComments`).

<objective>
Build `NotificationsModule` (`NotificationsService`, `NotificationsController`, `PortalActivityController`), wire status change hooks in `RoadmapService` and `ModerationService`, and prove notification delivery, deduplication/grouping, unread counting, and activity visit diffing through integration tests.

Purpose: Bridges product changes back to users who contributed feedback, fulfilling the core feedback-in / roadmap-out promise.
Output: Notifications API module, integration with roadmap & moderation services, unit/integration tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Signed-in User -> Notification API | Authenticated user reading notifications and marking them read |
| Internal Service Hook -> NotificationsService | Status changes triggering fan-out across discovered user IDs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information Disclosure | `NotificationsController` & `PortalActivityController` | high | mitigate | ASVS V14.4: Notifications and activity feeds expose only public post attributes and public status notes. Internal roadmap fields are strictly excluded. |
| T-04-02 | Tampering | `NotificationsController` mark-read | medium | mitigate | All mark-read operations are scoped to `where(eq(notifications.userId, currentUser.id))`. Users cannot read or acknowledge other users' notifications. |
| T-04-03 | Denial of Service / Flooding | Notification fan-out | medium | mitigate | Grouped UPSERT on `UNIQUE(user_id, post_id)` collapses rapid status moves on the same post into a single row, preventing table bloat and notification noise. |
</threat_model>

1. Create `apps/api/src/notifications/notifications.service.ts`:
   - `fanOutStatusChange(tx, opts)`:
     Query distinct user IDs from:
     - `posts.author_id WHERE id = opts.postId`
     - `votes.user_id WHERE post_id = opts.postId`
     - `comments.author_id WHERE post_id = opts.postId AND deleted_at IS NULL`
     Filter out `opts.actorId` and `null` users.
     For each stakeholder, execute:
     `INSERT INTO notifications (user_id, workspace_id, product_id, post_id, post_activity_id, read_at, created_at) VALUES (...) ON CONFLICT (user_id, post_id) DO UPDATE SET post_activity_id = EXCLUDED.post_activity_id, read_at = NULL, created_at = NOW()`
   - `getUnreadCount(userId)`: Query count of rows in `notifications` where `userId = userId` and `readAt IS NULL`.
   - `listNotifications(userId, limit)`: Query user notifications ordered by `createdAt DESC`, joined with `posts` and `postActivity`, formatting status change details and public note preview.
   - `markAllRead(userId)`: `UPDATE notifications SET read_at = NOW() WHERE user_id = userId AND read_at IS NULL`.
   - `markPostRead(userId, postId)`: `UPDATE notifications SET read_at = NOW() WHERE user_id = userId AND post_id = postId AND read_at IS NULL`.
2. Connect `NotificationsService` into:
   - `RoadmapService.moveItem` & `updateItem`: when status changes, call `fanOutStatusChange` for each linked post.
   - `ModerationService.changeStatus`: when status changes, call `fanOutStatusChange`.
3. Create `apps/api/src/notifications/notifications.controller.ts`:
   - `GET /api/v1/notifications/unread-count`: returns `{ count: number }`
   - `GET /api/v1/notifications`: returns `{ notifications: NotificationItem[] }`
   - `POST /api/v1/notifications/mark-read`: marks all read, returns `{ success: true }`
   - `POST /api/v1/notifications/:postId/read`: marks specific post notification read, returns `{ success: true }`
4. Register in `NotificationsModule` and `AppModule`.
5. Create `apps/api/test/notifications.test.ts`:

   - Verify actor is excluded.
   - Verify repeated status changes on the same post group into ONE notification row with updated activity and unread state.
   - Verify mark-read operations clear unread state.

   - `GET /`: Requires authenticated user (`@CurrentUser()`).
     1. Retrieve existing `lastVisitedAt` from `userProductActivityVisits` for `(user.id, portal.productId)`.
