# Quick 261107-052: Safe outbound webhook and push transport

Webhook and push registration now share a public-address policy, and both workers
send through one native HTTPS client with pinned DNS, hostname TLS verification,
a complete exchange deadline and bounded response allocation.

## Delivered

1. Webhook creation and URL updates reject non-HTTPS URLs, URL credentials,
   non-public IPv4/IPv6 literals, unsafe alternative IPv4 spellings, failed DNS,
   and DNS answers containing any non-public address. Updates retain tenant lookup
   before destination validation. API failures use controlled `invalid_url` errors.
2. Every delivery resolves and validates again, then supplies only the validated
   address to native socket lookup. Requests retain the original Host and TLS
   hostname, require certificate verification, disable pooled agents, and never
   follow redirects. A single 10-second production deadline starts before DNS
   and lasts through TLS/headers/body. Late DNS cannot open a connection. Response
   storage copies at most 8192 bytes; a full prefix closes the response and retains
   its HTTP status, while webhook diagnostic previews remain capped at 1000 chars.
3. Push registration uses the same policy. Push encryption/VAPID bytes come from
   installed web-push `generateRequestDetails`; only the shared transport performs
   network I/O. Explicit status handling preserves retries and 404/410 cleanup.
   Stored worker errors are fixed categories rather than raw destination details.

## RED/GREEN evidence

- Unsafe webhook creation returned **201 instead of 400** before validation.
- A destination changing to private DNS before delivery produced the old generic
  fetch failure instead of policy rejection. It now rejects before socket creation
  with no response preview.
- Unsafe push registration returned **201 instead of 400** before validation.
- Encrypted push delivery through the controlled HTTPS boundary stayed **pending
  instead of delivered** before routing web-push through the shared transport.
- Each behavioral RED was observed using the real HTTP/DB or worker/network seam.
  Regression and implementation changes were committed together per task rather
  than as separate RED-only commits.

## Decisions and deviations

- DNS/native request dependencies are injectable process boundaries. Production
  has no NODE_ENV bypass, private-address allowlist or configurable unsafe mode.
- Test fixtures map only declared hosts; the real policy/client remain active.
  A dedicated real TLS receiver tests certificate/hostname behavior. The existing
  webhook HTTP receiver is reached only by its explicit test socket adapter.
- The committed private key is a self-signed **test fixture only**, paired with
  its fixture certificate; production does not read either file.
- Push encrypted request details are generated locally before the transport's
  single DNS-to-response budget. This avoids two DNS budgets; no network I/O can
  occur before shared validation. All external I/O stays inside the fixed budget.
- A validation test initially left an extra subscription that broke an existing
  count assertion; HTTP cleanup fixed it in `4816005`. The 11 relevant policy/CRUD
  tests then passed, followed by the complete webhook suite after transport wiring.
