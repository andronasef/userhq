Facts found by reading the code, which shape the plan:
- Contrast defect. accentStyle (lib/accent.ts) writes --primary, --primary-foreground, --primary-text, --ring and --entity-accent as inline styles on the portal shell (data-shell="portal") and, through PortalAccentProvider, onto Radix portal content. Inline styles beat the `.dark` block in globals.css, so in dark mode --primary-text keeps its light-mode value. That value is either the raw brand colour (default accent #2563EB is 3.27:1 on the dark card, #1E3A8A is 1.6:1) or the fixed `#171717` fallback for light brands (invisible on the dark page). The light rule also checks only pure white, while the page background is #F6F8F7, so marginal colours fall just under 4.5:1 there.
- PortalFrame (components/portal/portal-frame.tsx) forwards the style object unchanged to the shell and to PortalAccentProvider. It needs no code change; the defect is the token it carries. The only caller that passes accentStyle is app/[ws]/[product]/layout.tsx.
- Text on the accent: --primary-foreground is chosen by whichever of white or black contrasts more with the brand colour, which is at least 4.58:1 for every colour, and it is overridden inline in both themes. So it cannot regress with the theme; the test pins it for the full colour set. A custom button text colour chosen by an admin is honoured as-is (the branding form already warns below 3:1) and is not asserted.
- Theme cookie. `userhq_theme` is written by saveThemePreference and read only by getStoredThemePreference. Nothing server-side reads it (grep: only lib/theme.ts and app/layout.tsx mention the key). The inline script reads storage only, so with empty or blocked storage and a cookie present the script paints System and hydration later flips to the cookie value, which is the flash. Decision (Claude's discretion, D-01 only requires remembering the choice): drop the cookie. Storage already remembers the choice, a script-set cookie gains no persistence over storage in Safari, and one store cannot disagree with itself. Stale cookies from earlier visits are harmless and expire by themselves.
- The inline script also has two smaller faults: a throwing storage read skips the whole script (even the OS dark scheme is not applied), and an unrecognised stored value is copied into dataset.theme.
- ThemeProvider starts at "system"/"light" and corrects after mount in a passive effect, so a stored-dark visitor sees the toggle on System for a paint. Its OS-change handler re-reads storage rather than the document, so with storage blocked an explicit Light chosen this session is overridden by System when the OS flips. Fix both from the document, which the head script has already resolved.
- Existing browser spec: apps/api/test/browser/appearance.spec.ts (describe "Appearance & Dark Mode"), seeded workspace and product, dark body background rgb(11, 17, 30), segmented switcher selectors already written. New cases go in that describe. The seeded product uses the default accent.

Not in this plan, recorded so it is not mistaken for coverage: the raw `text-primary`, `ring-primary` and focus-ring (--ring) utilities render the brand colour itself as text or outline, and text on `bg-muted` chips is not covered by the 4.5:1 guarantee (only page background and card are). The request names the --primary-text token and link/button text, so those call sites are left unchanged and flagged as a follow-up candidate. Older browsers without light-dark() (before 2024) drop --primary-text to the inherited foreground colour, which stays legible.
